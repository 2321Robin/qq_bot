# Privacy Notice

This document describes how the QQ Group Bot ("the bot") handles data
in its current implementation. It is a factual description of the
software's behavior, **not** a legal document or a promise of future
features.

## 1. Data processed

When the bot is running, it may process the following categories of data:

| Category | Examples | Source |
|---|---|---|
| Group identifiers | QQ group numbers | OneBot events from NapCatQQ |
| User identifiers | QQ user numbers | OneBot events from NapCatQQ |
| Message content | Text messages sent in groups | OneBot events from NapCatQQ |
| AI replies | Text generated by the configured AI model | Bot's AI client |
| Timestamps | Message timestamps | OneBot events from NapCatQQ |
| Quota usage | Per-group request/token counts and costs for the current day | Bot's quota service (SQLite) |
| Log identifiers | Process IDs, log file names, error messages | Bot's runtime logs |

## 2. Local storage

- Chat memory is stored in a **SQLite database** at the path configured
  in `.env` (`CHAT_MEMORY_PATH`, default `data/chat_memory.sqlite3`).
- Records are retained for a configurable number of days
  (`CHAT_MEMORY_RETENTION_DAYS`, default **3 days**).
- Expired records are cleaned up on each read or write operation.
- The database is **not** encrypted at rest.
- The database file is excluded from version control (`.gitignore`).
- **Layered memory (stage 2, `AGENT_ENABLED=true`):**
  - *Recent messages* — the most recent messages in a group, kept only
    within `CHAT_MEMORY_RETENTION_DAYS`.
  - *Short-term summaries* — only when `MEMORY_SUMMARY_ENABLED=true`, the
    bot summarizes messages that are about to expire. A summary records
    its source message IDs and an `expires` timestamp; the summary never
    extends the retention window of the underlying messages (both expire
    independently, both cleaned on read/write).
  - *Long-term preferences* — written **only** by the explicit user
    command `/记忆保存` (whole-group explicit opt-in, one entry per user,
    truncated to `MEMORY_PREFERENCE_MAX_CHARS` characters).
  - *Person observation cards* — only when `PERSON_OBSERVE_ENABLED=true`,
    an offline learning round (admin `/表达学习` or
    `scripts/learn_expressions.py`) stores **one short derived profile per
    user per group** (≤ `PERSON_OBSERVE_MAX_CHARS` characters, rolling
    overwrite). Message bodies are never stored in the card; the card is
    readable by the user themselves via `/记忆查看` and by the AI prompt
    builder for that user. Users who closed long-term memory
    (`/记忆关闭`) never get a card: the opt-out clears any existing card
    and blocks writes.
  - *Deletion scope* — `/记忆删除 全部` (or `/记忆关闭`) deletes the
    invoking user's own recent messages, AI replies, preference entry,
    observation card and any summaries related to those messages. It does
    **not** delete other users' messages, cards or data, and there is no
    mechanism that affects data of users other than the invoker.
- **Auto-chat tune log (default on):** when `AUTO_CHAT_ENABLED=true` and
  `AUTO_CHAT_TUNE_LOG_ENABLED=true` (the default), every autonomous reply
  appends one JSON line to `data/auto_chat_tune.jsonl` containing the
  trigger text, the recent context window (raw group id, raw user ids and
  message bodies) and the bot's reply. This file is a local review
  artifact for the deployer: it never enters logs, metrics, spans or the
  public repository (git-ignored), and it is not sent anywhere. Set
  `AUTO_CHAT_TUNE_LOG_ENABLED=false` to stop writing, or delete the file
  to remove past entries.
- **Group nicknames in prompts (opt-in, S11-AUTO-04):** with
  `AUTO_CHAT_NICKNAMES_ENABLED=true` the bot resolves members by their group
  card (falling back to QQ nickname) instead of the 用户A/B letter aliases in
  the auto-chat prompts and tune-log context lines. Per the deployer ruling
  (2026-10-25) there is **no periodic refresh**: the OneBot
  `get_group_member_list` call happens only when the current context contains
  user ids missing from the cache, and the result is persisted to the
  git-ignored `data/group_nicknames.json` (restarts reuse it; deleting the
  file forces a full refresh; renames lag until then). Nicknames are
  group-public information; they may therefore appear in model prompts (same
  provider boundary as the messages themselves) and in the deployer-local
  tune log. Raw user ids still never enter prompts, and a digit-only
  nickname (shaped like a QQ id) is dropped to the letter alias. With the
  flag off (default) or on any fetch failure the behavior is unchanged
  (letter aliases).
- **Learning-derived tables (opt-in):** when the expression-learning
  feature is enabled (`EXPRESSION_LEARN_ENABLED=true`), the learning
  round stores derived data in the chat SQLite database — sentence
  **templates** with an evidence digest and jargon terms with inferred
  definitions (migration 4 `expressions`/`jargon`, per group), plus the
  person observation cards described above (migration 5). Templates,
  digests and definitions are derived summaries, not message bodies;
  the underlying messages remain subject to the normal retention days.
  `/表达 禁用` and `/黑话 禁用` deactivate entries; removing the rows
  requires a SQLite client.
- **Logs contain no message bodies.** Runtime logs record only counts
  and category-level outcomes (retry attempts, circuit-breaker state,
  per-group failure counts); message text, raw QQ group/user numbers,
  access tokens, and WebSocket URLs with credentials are never written
  to logs.
- **Observability artifacts (stage 4):** structured JSON logs
  (`LOG_FORMAT=json`), Prometheus metrics and trace spans carry group and
  user identifiers only as **irreversible hashes** (sha256 truncated to
  16 hex chars, `group_`/`user_` prefixes); the same `request_id` flows
  through logs, spans (`trace_id`) and metrics. Message bodies, raw
  prompts, AI drafts and API keys never appear in logs, metrics, spans
  or reports. Hash prefixes make the channel obvious but are not
  reversible to the original integers.
- **Quota storage:** daily per-group request/token/cost counts
  (`quota_usage`) and quota events such as rate/cost denials
  (`quota_events`) are stored as raw integers in the chat SQLite
  database (same file as chat memory, `CHAT_MEMORY_PATH`), consistent
  with the existing integer storage convention.
- **Admin command exception:** the owner-facing admin commands `/配额`
  and `/最近故障` (authorized via `ADMIN_USER_IDS`) never reveal other
  groups' raw group numbers. `/最近故障` renders every cross-group scope
  id as an **irreversible hash** (sha256 truncated to 16 hex chars,
  `group_` prefix, e.g. `group_<hash>`), so those entries cannot be
  mapped back to raw integers. The raw-id exception therefore narrows to
  `/配额`, which displays the **current group's own** raw integer group
  number so an owner can map usage to that group. Raw identifiers appear
  only in the admin chat reply, never in logs, metrics, spans or
  reports.

## 3. External data transmission

- **AI Provider:** When a user triggers an AI chat (`ai ...` or @bot),
  the user's message and selected chat history are sent to the
  configured AI model provider (e.g., OpenAI, ZhiPu AI) over HTTPS.
  Which messages are included depends on the chat memory query and
  the user's explicit reference ("参考最近 N 条", "@某人", etc.).
  In agent mode (`AGENT_ENABLED=true`), the transmitted payload is the
  user prompt plus the token-budgeted memory layers (recent messages,
  summary, preference) and local knowledge selected by the Router; the
  same provider boundaries apply — nothing beyond the selected prompt
  context and tool results is sent.
- **Search Provider (optional):** When `SEARCH_ENABLED=true` and a
  search-like query is detected, the query and a short system context
  are sent to **Tavily** (https://tavily.com/) over HTTPS. Search result
  excerpts are treated as untrusted data; the bot never re-fetches the
  result URLs and only reports URLs the search tool actually returned.
- **Scheduled life reports (optional, stage D):** When
  `SCHEDULED_JOBS` enables `life_morning`/`life_evening`, the bot fetches
  news, hot lists and gaming-community posts from the deployer's own
  60s-API instance (`REPORT_60S_BASE_URL`). These requests carry **no
  group ids, user ids or message content** — they are anonymous content
  fetches on a fixed schedule. When `REPORT_AI_ENABLED=true`, only the
  fetched news titles (no user data) are sent to the AI provider for
  reformatting; the deterministic check and template fallback keep the
  provider from becoming a source of facts.
- **No other external transmission:** The bot does not phone home,
  send analytics, or transmit group data to any other endpoint.

Deployers should review the privacy policies of their chosen AI
provider and Tavily, and are responsible for the upstream sources
proxied by their self-hosted 60s instance.


**自主群聊插话（S7-AUTO）：** 开启 `AUTO_CHAT_ENABLED` 后，机器人可能自主回复未被 @ 的群消息。为此，该群最近 `AUTO_CHAT_CONTEXT_MESSAGES` 条消息（默认 10 条）会作为上下文发送给已配置的模型服务商，用于插话决策与回复生成——与既有 AI 对话的记忆上下文同一边界、同一服务商集合。是否插话的决策结果只以计数指标（`qq_bot_auto_chat_total{stage,result}`）与哈希维度记录，日志不落消息正文、prompt 或明文群号/用户号；"点名"匹配、敏感词与负反馈词表仅在本进程内做子串匹配，不出网。

## 4. Access and deletion

- The SQLite database is entirely under the deployer's control.
- **User-facing deletion commands (stage 2):**
  - `/记忆删除 全部` (or `/记忆关闭`) — deletes the invoking user's own
    recent messages, AI replies, preference entry, observation card and
    related summaries from the chat memory database. Deletion is immediate
    and survives restart; no deleted content is fed into later prompts.
  - `/记忆删除` — deletes only the invoking user's saved preference entry.
  - These commands affect only the invoking user's data, never other
    users' messages.
- To delete all data:
  1. Stop the bot.
  2. Delete the SQLite file at `CHAT_MEMORY_PATH` (default
     `data/chat_memory.sqlite3`), or delete individual rows using a
     SQLite client.
  3. Delete `data/auto_chat_tune.jsonl` if the tune log was enabled
     (or disable `AUTO_CHAT_TUNE_LOG_ENABLED` to stop future writes).
  4. Optionally delete the `logs/` directory for runtime logs.
- There is currently no mechanism to notify users when their data is
  deleted or to respond to data subject access requests automatically.

## 5. Configuration boundaries

The following settings **reduce** the scope of data processing but do
**not** constitute full anonymization, consent management, or legal
compliance by themselves:

- `ALLOWED_GROUP_IDS` — limits which groups the bot responds to.
- `ADMIN_USER_IDS` — authorizes the owner-facing admin commands
  `/配额` and `/最近故障` (quota view and recent quota events).
- `CHAT_MEMORY_RETENTION_DAYS` — limits how long messages are kept.
- Logging is file-based; log files are not rotated or automatically
  deleted by the bot.

## 6. Screenshots and demos

Before publishing any screenshots of the bot in use, the deployer must:

- Irreversibly redact group names, group numbers, QQ numbers, avatars,
  nicknames, timestamps, notification bar content, QR codes, URLs,
  tokens, and unrelated chat messages.
- Re-export the image and verify that EXIF and PNG text metadata
  contain no residual identifiers.

## 7. Deployer responsibility

- This privacy notice describes the software's current behavior.
  It does **not** replace:
  - Informing group members that a bot is present and what data it
    records.
  - Obtaining legally valid consent where required by applicable law.
  - Reviewing the AI provider's and Tavily's terms of service and
    privacy policies.
  - Configuring the bot in a manner compliant with local regulations.
- The deployer is the data controller for any personal data processed
  through this bot.

## 8. Changes

If the bot's data handling behavior changes, this document will be
updated to reflect the new behavior. The deployer should review this
document after each update.
